---
title: "Run a node"
description: "Operating the sequencer and the publisher."
---

Two processes, with **very different risk profiles**. Run them separately.

## Sequencer

Batches queued commitments into the tree and serves Merkle paths.

```bash
POOL_ADDRESS=0x... DEPLOY_BLOCK=... RELAYER_MNEMONIC="..." \
  npm run start:sequencer
```

<Warning>
**It must not sleep.** While it is down nobody can obtain a Merkle path, so nobody can build a
bet proof. A sleeping sequencer is a closed market, not a slow one.
</Warning>

If compromised it can stall the market. It cannot steal, cannot insert a leaf nobody queued,
and cannot learn who bet what.

Health: `GET /health`. Merkle paths: `GET /path?commitment=0x...`.

## Publisher

Decrypts the encrypted pool total and publishes a coarse ratio.

```bash
POOL_ADDRESS=0x... ACCUMULATOR_ADDRESS=0x... ENCRYPTED_POOL_ADDRESS=0x... \
MARKET_IDS=8,10 COMMITTEE_SECRET=... PUBLISHER_PRIVATE_KEY=0x... \
  npm run start:publisher
```

<Warning>
**This process holds the committee key.** Anyone who obtains it can decrypt every individual
bet in every market, retroactively. It belongs in its own environment, with the secret
injected at runtime and never written to a committed file or a log.
</Warning>

It may sleep. Stale odds are cosmetic — no payout reads them.

`PUBLISHER_PRIVATE_KEY` is deliberately a different key: it pays gas and decrypts nothing, so
a leaked hot wallet is not a privacy incident.

## RPC

Use a private endpoint. Measured limits on `eth_getLogs`: Monad's public RPC caps at 100
blocks, Alchemy's free tier at 9.

Neither service scans logs — counts and batch boundaries are read from contract storage
precisely because no endpoint will serve the history — but the rest of the RPC load still
benefits.
